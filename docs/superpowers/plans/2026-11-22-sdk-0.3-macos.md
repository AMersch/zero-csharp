# Zero C# SDK 0.3 (macOS, stable framework name) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `osx-arm64` a target from every build machine, add macOS arm64
as a build machine if the spike passes, and name the framework `zero03` from a
library-format property instead of the SDK version.

**Architecture:**
- **macOS programs:** bflat compiles with `--os macos -c`. The package's lld,
  run as `ld64.lld`, links the object with Mach-O runtime objects and our own
  `libSystem.tbd` from the SDK payload.
- **The macOS build machine:** a NativeAOT-published bflat with Microsoft's
  osx-arm64 JITs, in a new `ZeroCSharp.Bflat.osx-arm64` package. It's gated by
  a spike on a GitHub macOS runner.
- **The framework:** it comes from `<ZeroFramework>` in `sdk/version.props`.
  Library packages record the SDK version that built them, and ZERO002
  refuses newer ones.

**Tech Stack:** MSBuild project SDK, NuGet, bflat (fork), LLVM lld 20.1.8
(ELF, COFF and Mach-O flavors), clang (cross-compiling Mach-O objects),
GitHub Actions (ubuntu, windows, macos arm64 runners), bash tests
(`sdk/test/run.sh`).

**Spec:** `docs/superpowers/specs/2026-11-22-sdk-0.3-macos-design.md`

## Global Constraints

- Only the .NET 10 SDK on a user's build machine: no Xcode, no Command Line
  Tools, no Apple SDK file. CI's macOS runners may use Xcode to make packages.
- Ship no file of Apple's SDK. `libSystem.tbd` is written by us.
- Version `0.3.0`, framework `zero03`. 0.2 projects break only by the
  framework change and the re-pack it needs.
- osx-arm64 programs: Mach-O arm64, ad-hoc signed, minimum macOS 11.0. The
  output has no extension, in `bin/<config>/zero03/osx-arm64/` when chosen,
  like other targets.
- Not in scope: Intel Macs (osx-x64), WebAssembly or DOS in the SDK,
  notarization or Developer ID signing, other dylibs (documented only).
- Releases carry bflat from the fork's master (`check-tag.sh`, `BFLAT_REF`).
  Publishing is by trusted publishing on an `sdk-v*` tag.
- Nothing downloaded runs natively on the user's Mac: the spike runs on a
  GitHub macOS runner.
- Ask the user before:
  - merging, tagging or publishing;
  - pushing the fork's master;
  - adding assets to a fork release.
- Never commit `docs/llama-plan.md`. Stage files by name.

## Review Focus

1. **A program that calls libm or pthread functions, built for
   osx-arm64.** Llama uses `expf`/`sqrtf`, and `Parallel.For` uses pthreads.
   It should link and run on a Mac, not fail with an undefined symbol.
   - Task 3: `mac_target_links_libm_and_threads`.
   - Task 4: the storyteller and the threads fixture run on the macOS runner.
2. **osx-arm64 next to the other targets in one project.** Programs for
   several targets should stay side by side, and `dotnet clean` should
   remove all of them, the Mac one included.
   - Task 3: `targets_side_by_side` gains osx-arm64.
3. **Paths with spaces or non-ASCII characters through ld64.lld.** The
   project folder and the packages folder are the cases to cover.
   - Task 3: `mac_target_path_with_spaces`.
4. **A library from a newer patch release of the SDK, or from the same
   one.** ZERO002 only for newer versions; equal and older ones build.
   Prerelease suffixes shouldn't crash the comparison.
   - Task 1: `newer_sdk_library`.
5. **On Windows, `ld64.lld` comes from `lld.exe`.** The Mach-O link has to
   work there without symlinks.
   - Task 4: the `windows` job builds osx-arm64, and `windows-built-macos`
     runs the result.
