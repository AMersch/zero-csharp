# SDK 0.10 (the C64 with `dotnet build`): plan

Design: `docs/superpowers/specs/2026-11-24-sdk-0.10-c64-design.md` (approved,
spikes passed). Each task ends with its tests passing and a commit.

## Task 1: the Python tools in C#

`sdk/ZeroCSharp.Bitcode/`: a .NET 10 console program, `zero-bitcode`, with
the three tools as commands, same arguments as the scripts:

    zero-bitcode ll2mos OUTDIR IN.ll...
    zero-bitcode wasm2mos IN.o OUT MODULE.ll...
    zero-bitcode wasm2i386 IN.o OUT

- Output byte for byte the Python scripts' (always `\n` line ends, UTF-8
  without a byte order mark), and the same failures, as `<tool>: <message>`
  on standard error with exit code 1.
- `scripts/compare-bitcode-tools.sh` runs both on every program in
  `bin/c64/obj` and `bin/dos/obj` and diffs. Run locally on the 19 C64
  programs and the DOS programs.
- `build.sh` builds the tool once (`bin/tools/`) and uses it; Python stays in
  the repository until CI has compared on Linux.

## Task 2: CI compares, then Python goes

- The `c64` job runs the comparison after its tests.
- Once green: delete `c64/*.py` and `dos/wasm2i386.py`, drop Python from
  `setup.sh` and the docs.

## Task 3: the tool cache and the compiler step in the SDK

- The SDK downloads NativeAOT-LLVM (host build; linux-arm64 in Docker on a
  Mac) and llvm-mos into a per-user cache, checking SHA-256.
- `docker info` before using Docker on a Mac; errors name Docker Desktop,
  Colima and Podman.
- The payload gains zerocore built with `-d WASM`, `c64/runtime.c`, and the
  `zero-bitcode` tool.

## Task 4: `ZeroTarget=c64`

- bflat build-il, NativeAOT-LLVM, `zero-bitcode`, llvm-mos (`clang --config
  mos-c64.cfg`, with the "ran out of registers" retry), into
  `bin/.../c64/<Name>.prg`.
- Tests: `sdk/test/run.sh` builds Tiny for the C64 on Linux (and runs it in
  VICE there), Windows builds it; the Mac by hand.
- Docs (install, build for the C64), version 0.10.0, release.
