# Zero C# SDK 0.3: macOS, and a framework name that stays put: design

Approved approaches: 2026-11-22 (the user: "yes all works"). The Design
section becomes final when the user approves this document; planning waits
for that.

## Intent

0.2 made Windows a build machine. A Mac is still the odd one out: on macOS,
`dotnet build` of a zero project compiles the C# and then stops with "Zero C#
can't make native programs on macOS yet", and no build machine can make a
macOS program. The repository can (`./build.sh --mac`), but only with a Linux
container for bflat and Xcode's clang and linker for the link. The user works
on a Mac.

0.3 has to be a new framework (`zero03`), because the framework name today is
`zero<major><minor>`. Every minor release forces everyone to re-pack their
libraries, for no reason when the library format hasn't changed. 0.3 makes
that change the last forced one.

## Goals

1. **osx-arm64 as a target from every build machine.**
   `dotnet build -p:ZeroTarget=osx-arm64` on Linux x64/arm64, Windows x64 and
   macOS arm64 makes a Mach-O program that runs on Apple Silicon Macs. Only the
   .NET 10 SDK is needed: no Xcode, no Apple SDK.
2. **macOS arm64 as a build machine.** A new package,
   `ZeroCSharp.Bflat.osx-arm64`. On a Mac, `dotnet build` makes a macOS
   program by default and can build all four targets.
   - This depends on a spike (below). If the spike fails, 0.3 ships without
     the build machine, and the docs keep saying macOS compiles only.
3. **A framework name tied to the library format, not the SDK version.**
   `zero03` stays the framework of 0.3, 0.4 and later, until zerocore's or the
   SDK library's format really breaks.
   - A program refuses, with a clear error, a library built by a newer SDK
     than its own, because that library may use APIs this SDK lacks.
4. Everything from 0.2 keeps working, with tests on all four build machines
   and the smoke test after release.

## Non-goals

- Intel Macs (osx-x64), as a target or a build machine.
- WebAssembly and DOS in the SDK. WebAssembly is a candidate for 0.4.
- Notarization or Developer ID signing. Programs get an ad-hoc signature,
  which is what Apple Silicon needs to run a program built on the same Mac,
  or one downloaded without a quarantine flag.
- Programs that link other macOS frameworks or dylibs beyond libSystem.
  They still work through `ZeroNativeInput` with the user's own `.tbd` or
  `.dylib`, documented but not tested.
- Changing bflat's compiler version, or moving to .NET 11's compiler.

## Anti-goals

- Requiring Xcode, the Command Line Tools or any Apple SDK file on a user's
  build machine. CI's macOS runners may use Xcode to make the packages (my
  call: that is where bflat itself gets built for macOS).
- Shipping any file of Apple's SDK in a package: the `.tbd` stub is ours.
- A 0.3 that breaks 0.2 projects beyond the framework change (`zero02` →
  `zero03`) and the re-pack it needs.

## Constraints

- **Today's macOS path** (`build.sh` `build_mac_objects` / `build_mac_link`):
  - bflat compiles with `--os macos --arch arm64 -c` into a Mach-O object.
  - clang links it with `mac/runtime.c` (main, `get_nprocs`, and
    `clock_gettime` mapped to `clock_gettime_nsec_np`) and
    `zerocore/native/mac-arm64.S`.
  - Options: `-dead_strip`, and `-alias` from `section$start$__DATA$__modules`
    to `___start___modules` (and from `$end` to `___stop___modules`).
  - Apple's `nm` calls ILC's Mach-O object "malformed" (filesize > vmsize), but
    ld64 links it.
- **zerocore and lib bind C functions at link time** (`-i libc`,
  `-i libm.so.6`). On macOS all of them live in libSystem
  (`/usr/lib/libSystem.B.dylib`), libm included.
- **The fork's lld** (LLVM 20.1.8, `tools/build-lld.sh`, release `lld-20.1.8`)
  is one binary for every flavor. Invoked as `ld64.lld` it is the Mach-O
  linker, if the build includes the MachO port (LLVM's default for lld).
  - The Linux builds need only libc, libm and libgcc_s.
  - The Windows one is LLVM's official `lld.exe`.
- **bflat's compiler parts are per build machine:**
  - The JIT libraries and `libjitinterface` come from
    `bflattened/runtime` `v10.0.0-rc.1.25527.1`.
  - `lld` and `llvm-objcopy` come from `bflattened/blobs` `v1.3`.
  - Both publish only Linux and Windows builds.
  - The fork already replaces the RC1 JIT with the one from Microsoft's GA
    package (`runtime.<rid>.microsoft.dotnet.ilcompiler` 10.0.0). Microsoft
    publishes that package for osx-arm64 as well.
- **Standing rules:**
  - Releases come from the fork's master (`check-tag.sh`).
  - Packages go out by trusted publishing.
  - Running downloaded third-party code natively on the user's Mac needs the
    user's approval. The spike avoids that by running on a GitHub macOS
    runner (my call).
- **Microsoft's osx-arm64 compiler package has every JIT a Mac needs.**
  `runtime.osx-arm64.microsoft.dotnet.ilcompiler` 10.0.0 carries the same JITs
  as the Linux layouts, hosted on arm64 macOS: `libclrjit_universal_arm64_arm64`,
  `_universal_arm_arm64`, `_unix_x64_arm64`, `_win_x64_arm64`,
  `_win_x86_arm64`, plus `libjitinterface_arm64.dylib`. Checked 2026-11-22 by
  listing the package. So a Mac can target all four.
- **bflat can't build itself for macOS.** The fork's `BuildLayouts` makes each
  host's bflat with bflat (`--os:<host>`), but bflat only compiles for macOS
  (`--os macos` needs `-c` and `--stdlib:none`).

## Approaches

**Linking macOS programs:**

| Approach | Trade-offs |
|---|---|
| Link with Xcode's clang on a Mac only | Little work. Needs Xcode, and only Macs can build for macOS. |
| `ld64.lld` from every build machine, with our own `libSystem.tbd` **(chosen)** | Keeps "only the .NET SDK". All build machines get all four targets. Costs a hand-written stub and proving ld64.lld on ILC's objects. |

**The macOS build machine:**

| Approach | Trade-offs |
|---|---|
| Build bflat for osx-arm64 ourselves, after a spike **(chosen)** | Uses Microsoft's osx-arm64 JIT and `libjitinterface`, and LLVM 20.1.8's lld and objcopy built on a macOS runner. Risk: the GA `libjitinterface` against bflat's RC1 managed compiler. |
| Leave it out | No risk, but the user's own machine still can't build. |

**The framework name:**

| Approach | Trade-offs |
|---|---|
| Keep `zero<major><minor>` | Simple, but every minor release forces a re-pack. |
| A hand-kept library format number, `zero03` **(chosen)** | Changes only when the format breaks. A newer-SDK library is caught by its own error, since NuGet can't see it. |

## Design

### 1. The framework name (`zero03`, then stable)

- `sdk/version.props` gets `<ZeroFramework>zero03</ZeroFramework>`, separate
  from `ZeroSdkVersion`. Every place that derives `zero<major><minor>` reads
  it instead:
  - `Sdk.props` (`ZeroSdkTfm`);
  - pack paths (`lib/zero03/`);
  - `sdk/test/run.sh` (`TFM`);
  - the templates' and the docs' mentions.
- **When to change it:** only when a library built by the previous framework
  can't work with the new SDK. That is, when zerocore's or the SDK library's
  types or members are removed or changed, or the native ABI between them and
  programs changes. Adding members isn't a reason. The rule goes in
  `sdk/README` (or the release notes section of `install-with-dotnet.md`) and
  in a comment next to the property.
- **ZERO002, a library from a newer SDK.** A library packed by
  `ZeroCSharp.Sdk` carries the SDK version that built it:
  `build/<PackageId>.props` adds an item
  `<ZeroLibraryBuiltWith Include="<PackageId>" SdkVersion="0.3.4" />`.
  - The consuming SDK fails the build with ZERO002 when any such item's
    `SdkVersion` is newer than its own, comparing major.minor.patch with
    MSBuild's version functions.
  - The message names the library, both versions, and "update ZeroCSharp.Sdk
    in the project's Sdk attribute".
  - Project references build with the same SDK, so they need no check.
  - Libraries packed by 0.1 or 0.2 don't matter: they are `zero01`/`zero02`,
    and NU1202 already refuses them.
- ZERO001 (setting TargetFramework) and NU1202 (another framework's library)
  stay as they are.

### 2. osx-arm64 as a target

- **The payload** (`build.sh --sdk-payload`) gains `native/osx-arm64/`:
  - `runtime.o`: `mac/runtime.c`, compiled for arm64 Mach-O.
  - `zerocore.o`: `zerocore/native/mac-arm64.S`.
  - `libSystem.tbd`: our text stub. Install name
    `/usr/lib/libSystem.B.dylib`, target `arm64-macos`, listing every C
    function zerocore and the SDK library import, plus a documented set of
    common libc/libm/pthread functions.
- **Where the payload's objects get built:**
  - Mach-O objects can't be made by the Linux payload job's gcc.
  - The builder chooses between clang with `-target arm64-apple-macos11` in
    the payload job, or a macOS job whose output the payload job takes.
  - `runtime.c` declares its own prototypes, so no Apple headers are needed.
- **`Sdk.targets` for `ZeroTarget=osx-arm64`:**
  - bflat runs with `--os macos --arch arm64 -c`, writing an object in `obj/`.
  - The SDK then runs the package's lld as `ld64.lld` (a copy or a symlink
    named so, or `-flavor darwin`) with:
    - `-arch arm64 -platform_version macos 11.0 11.0`;
    - the object, `runtime.o`, `zerocore.o` and `libSystem.tbd`;
    - `-dead_strip`;
    - the two module-list aliases (`-alias` or ld64.lld's
      `section$start`/`section$end` symbols, whichever works);
    - `-o` the program.
  - ld64.lld signs arm64 output ad hoc by default. The builder confirms the
    signature (`codesign -v` on the macOS runner).
  - The output has no extension, in `bin/<config>/zero03/osx-arm64/` like
    any other chosen target.
- **Unknown symbols:** a program's `DllImport` that libSystem lacks fails the
  link with ld64.lld's "undefined symbol" error naming it. The docs say how to
  add a library (`ZeroNativeInput`).
- **Linux, Windows and macOS-hosted builds all use this one path.** There's
  no Xcode path in the SDK.

### 3. macOS as a build machine (after the spike)

- **bflat itself for macOS** (my call): published with Microsoft's NativeAOT,
  `dotnet publish -r osx-arm64 -p:PublishAot=true`, on a macOS runner. This is
  outside `BuildLayouts`' bflat-builds-bflat step. The layout's other parts
  are assembled as for the other hosts:
  - the managed compiler (`BFlat.Compiler`);
  - the refs and the target libraries;
  - the JITs and `libjitinterface` from Microsoft's osx-arm64 package;
  - lld.
- **The spike** is a throwaway, on a GitHub macOS arm64 runner, so nothing
  downloaded runs on the user's Mac:
  - Build that bflat.
  - Compile Hello and Llama with it for **all four targets**: `linux-x64`,
    `linux-arm64`, `win-x64`, and `osx-arm64` (`--os macos -c`). Link them as
    the SDK would.
  - It passes if they link and print the same output as the Linux-hosted
    bflat's programs, each run on its own system, as CI's `*-built-*` jobs do.
  - Its result decides whether goal 2 ships.
- **Where the layout is built** (my call): in `sdk.yml`, a `bflat-macos` job
  on a macOS runner builds it from the fork's `BFLAT_REF` source.
  - It's cached by fork commit, like the `bflat` job's layouts.
  - Provenance is the same as the other packages': the fork's master at
    release (`check-tag.sh`).
- **If it passes, the fork gains:**
  - an `osx-arm64` layout build (a script or target run on a macOS runner);
  - an `LldRid` `osx-arm64`, with `lld-osx-arm64.tar.gz` added to the
    `lld-20.1.8` release, built by `tools/build-lld.sh` on a macOS runner (the
    lld.yml workflow);
  - an `llvm-objcopy` for macOS, if the layout needs one.
- **`ZeroCSharp.Bflat.osx-arm64`:**
  - trimmed like linux-x64, by mapping that list. `.so` becomes `.dylib`, and
    the imported dylibs are checked with `otool -L` instead of `objdump`.
  - `ZeroHostRid` becomes `osx-arm64` on macOS arm64.
  - The "can't make native programs on macOS" error stays only for Intel
    Macs, with a reworded message.
- **Ad-hoc signatures:** the package's executables and dylibs (bflat, lld,
  the Microsoft dylibs) must run when NuGet extracts them on a Mac. They are
  ad-hoc signed or Microsoft-signed, and NuGet sets no quarantine flag. CI
  proves it on a clean `macos` runner.

### 4. CI and release

- **`sdk.yml`:**
  - The existing `macos` job becomes a full test job on an Apple Silicon
    runner, running `run.sh` with native programs.
  - A new `trim-macos` job.
  - New `*-built-macos` jobs: programs built for osx-arm64 on Linux x64,
    Linux arm64 and Windows, run on the macOS runner, like
    `windows-built-linux`.
  - The Mac-built Linux and Windows programs are run on their own systems.
- **`check-tag.sh`:** unchanged, apart from the new package.
- **`sdk-smoke.yml`:** adds a `macos-latest` row and builds `osx-arm64` from
  every row.
- **Tests:** existing ones generalize over `HOST_RID` (`osx-arm64`). New ones:
  - mac programs from every build machine run and print the expected output
    (Hello and the storyteller);
  - the program is ad-hoc signed;
  - an undefined C function fails with its name;
  - ZERO002 for a library from a newer SDK, and none for an older or equal
    one;
  - the framework is `zero03` from `ZeroFramework`, not from the version.
- **Docs:**
  - `install-with-dotnet.md`: Mac as a build machine, four targets, `zero03`
    and the re-pack note, the framework rule, ZERO002.
  - `create-a-library.md`: the framework rule.
  - `concepts/limits.md`: Intel Macs; other dylibs.
  - The README's support matrix.

## Left to the builder

- `-alias` versus `section$start`/`section$end` in ld64.lld. Whichever links
  ILC's object and lets zerocore find its modules.
- How lld is run as `ld64.lld` on Windows, where symlinks are awkward
  (`-flavor darwin`, if this lld accepts it, or a copy).
- Where the Mach-O runtime objects are compiled (Linux clang cross, or a macOS
  job).
- The libc/libm/pthread list in `libSystem.tbd`, beyond what zerocore and the
  library import.
- The spike's exact scripts, and whether a GA-vs-RC1 `libjitinterface`
  mismatch can be bridged (for example by building `libjitinterface` from the
  RC1 sources on macOS). If it can't be bridged cheaply, report and drop
  goal 2 for 0.3.
- Package and job names beyond the ones fixed above.
