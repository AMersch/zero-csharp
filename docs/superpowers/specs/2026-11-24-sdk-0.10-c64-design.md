# Zero C# SDK 0.10: the Commodore 64 with `dotnet build`: design

Agreed so far (2026-11-24, the user): the C64 in the SDK is worth doing on
Linux and Windows natively and on a Mac with Docker ("we can tell user to use
docker"). Microcontrollers matter more than the C64, and come next; this
release builds the part they will share. Design approved 2026-11-24 (the
user: "ok"); planning waits for the spikes below.

## Intent

The repository builds C64 programs (`./build.sh --c64`, PR #38) on macOS and
x64 Linux, tested in CI (PR #41). An SDK user can't: `dotnet build` knows only
the targets bflat compiles (Linux, Windows, macOS, UEFI).

The C64 goes through a different compiler. bflat makes IL, NativeAOT-LLVM
turns it into LLVM bitcode for wasm32, `c64/ll2mos.py` rewrites that for the
6502's 2-byte addresses, and llvm-mos compiles and links it with
`c64/runtime.c`. WebAssembly and DOS use the same route, and so would a
Cortex-M microcontroller, with LLVM's ARM code generator in place of llvm-mos.

0.10 puts that route in the SDK, with the C64 as its first target.

## Goals

1. **`dotnet build -p:ZeroTarget=c64`** makes `bin/.../c64/<Name>.prg`, on:
   - Linux x64 and Windows x64, with nothing installed beyond the .NET SDK;
   - macOS on Apple Silicon, with Docker running.
2. **Tools fetched on first use, not shipped.** The first C64 build downloads
   NativeAOT-LLVM (40 MB unpacked) and llvm-mos (110 to 200 MB to download,
   about 700 MB unpacked, less if trimmed) from their own
   releases, checks their SHA-256 against values in the SDK, and keeps them in
   a per-user cache shared by all projects and SDK versions that use the same
   tool versions. No new nuget packages.
3. **A clear stop when something is missing,** with what to do: Docker on a
   Mac, no network on the first build, a cache folder that can't be written.
4. **No Python.** `ll2mos.py` and `wasm2mos.py` become C#, run by the SDK.
   The repository's scripts use the C# version too, and CI checks that its
   output matches the Python version's on every C64 sample before Python is
   retired.
5. **Running:** VICE stays the user's install (`brew install vice`,
   `apt install vice`). The docs say how to run a `.prg`, including Linux's
   missing ROMs. A `dotnet run` for the C64 is a stretch goal.
6. **Shared parts reusable by the next bitcode target:** the tool cache, the
   NativeAOT-LLVM step (native or in Docker), and the zerocore build for
   bitcode targets.

## Non-goals

- Linux arm64 as a build machine for the C64 (llvm-mos has no build for it).
- A Mac without Docker. That needs NativeAOT-LLVM built for Apple Silicon
  (Microsoft's last macOS build, 9.0.0-alpha of March 2024, is Intel-only and
  lacks the wasm code generator; checked 2026-11-24). A later release may
  build it, which would also remove Docker for every bitcode target.
  Docker-compatible tools without Docker Desktop's licence (Colima, Podman)
  should work too; the error message names them.
- WebAssembly, DOS or Cortex-M in the SDK in this release.
- Disk images, real hardware, or C64 programs that don't fit the 50 KB the
  repository's samples fit.

## Follow-up decision: Docker and microcontrollers

Cortex-M would use the same route, so on a Mac it would need Docker too. That
is fine for the C64, a hobby target, and a real barrier for microcontrollers,
which matter more. Decide after the first Cortex-M spike runs C# on a
microcontroller: the plan of record is to build NativeAOT-LLVM for Apple
Silicon (as the fork builds bflat for macOS), which removes Docker on a Mac for
every bitcode target at once. The alternative, a 32-bit ARM target in bflat,
would rule out Cortex-M0+ and assumes double-precision floating-point hardware
that Cortex-M chips don't have.

## Open questions, to settle with spikes before planning

1. **Windows host: done, works (2026-11-24).** On a GitHub Windows runner,
   the win-x64 NativeAOT-LLVM and llvm-mos's Windows build, with the Python
   tools, made Tiny and Paddles byte for byte identical to the Mac's .prg
   files. Windows' llvm-mos has no `mos-c64-clang` (on Unix that is a link to
   `clang` whose name picks the config); use `clang --config mos-c64.cfg`.
2. **Docker on a Mac: done, works (2026-11-24).** The linux-arm64
   NativeAOT-LLVM in a stock `ubuntu:24.04` container, with the folders
   mounted at the same path inside (so paths with spaces pass through as
   they are), made bitcode identical to the repository's build apart from
   embedded file names. Still to write: the message when Docker isn't
   running (`docker info` fails first).
3. **What the SDK payload adds:** zerocore built with `-d WASM` (as
   `bin/c64/System.Private.CoreLib.dll`), and `c64/runtime.c`, compiled by
   llvm-mos at build time or shipped as an llvm-mos object.
4. **CI:** GitHub's macOS runners have no Docker, so the Mac host can only be
   tested by hand. Linux gets a full test (build and run in VICE), Windows a
   build test.

## Rough order of work

1. Spikes 1 and 2.
2. `ll2mos` and `wasm2mos` in C#, matched against Python on every C64 sample.
3. The tool cache and the NativeAOT-LLVM step in the SDK.
4. `ZeroTarget=c64`, its tests, docs, and the release.
